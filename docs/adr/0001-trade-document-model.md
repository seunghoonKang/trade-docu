# 무역서류 도메인 모델 — 거래 건 → 선적 → 문서

하나의 거래를 **거래 건(Deal)** 으로 두고, 그 아래 분할선적인 **선적(Shipment)**, 그 아래 **문서(Document)** 를 두는 2계층 구조를 채택한다. 문서는 **양식(Template) × 데이터** 로 생성하며, **PI는 거래 건 레벨**(주문 전체 견적, 보통 1장), **CI·PL은 선적 레벨**(출고분마다)이다. 거래 건은 품목별 **주문 수량**, 선적은 **배분 수량** 을 가져 **잔여 수량**을 자동 계산한다(수량 위반은 차단이 아니라 경고).

## 왜

기존 구조는 flat `invoices` 테이블 1행 = 문서 1개(주로 PI)였다. 그러나 무역 현실에서 한 주문은 **분할선적**되어 선적마다 CI/PL이 따로 나오고, 세 문서는 하나의 거래로 묶여야 한다. flat + `doc_type` 만으로는 ① 분할선적, ② 잔량 추적, ③ 한 거래의 멀티문서 묶음을 표현할 수 없어 2계층 모델을 택했다.

## Considered Options

- **flat `invoices` + `doc_type`** — 변경 최소이나 분할선적/잔량/거래 묶음을 표현 못 해 기각.
- **거래 건 → 선적 → 문서 (채택)** — 무역 현실에 정합. 단일 선적 케이스는 기본 선적 1개로 자연 degrade.

## 범위 제외

**원산지증명서(CoO)** 는 한국에서 대한상공회의소·세관 등 공인기관이 발급하므로 앱 자체 생성 대상이 아니다. v1 양식은 **PI / CI / PL** 3종.
